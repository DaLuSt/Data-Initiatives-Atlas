# GitHub Pages Deployment

How the Interactive Atlas is built and published.

**Site URL:** <https://dalust.github.io/Data-Initiatives-Atlas/>

---

## The two workflows

Validation and deployment are deliberately separate, so an unvalidated pull
request can never reach the published site.

```
   Pull request                          Push to main
        │                                     │
        ▼                                     ▼
 .github/workflows/                  .github/workflows/
    validate.yml                         pages.yml
        │                                     │
   validate YAML                        validate YAML
   validate IDs                         validate IDs
   validate relationships               validate relationships
   validate links                       validate links
   validate sources                     validate sources
   graph generator tests                graph generator tests
   graph builds (--check)               generate graph
        │                                     │
        ▼                                     ▼
    PASS / FAIL                          build site
   (no deployment)                            │
                                              ▼
                                      deploy to GitHub Pages
```

### `validate.yml` — pull requests

Runs on `pull_request` → `main`, on `push` → `main`, and on demand
(`workflow_dispatch`).

1. `validation/run_all.py` — the five repository checks.
2. `tools/test_build_graph.py` — 32 generator tests.
3. `tools/build_graph.py --check` — proves the graph still builds from this
   branch's data, without writing anything.

**It never deploys.** There are no `pages` permissions in this workflow at
all.

### `pages.yml` — deployment

Runs on `push` → `main` when relevant paths change, and on demand.

It re-runs the full validation suite and the generator tests *before*
building, so a commit that reached `main` with broken data fails the deploy
rather than publishing a broken Atlas. It then regenerates the graph, writes
a statistics summary to the job summary, and uploads `site/` as the Pages
artefact.

The `paths:` filter covers every entity folder, `metadata/`, `tools/`,
`validation/`, `site/` and the workflow itself. A change to `progress/` or
`discovery/` does not trigger a redeploy, because it cannot change the
graph.

`concurrency: pages` with `cancel-in-progress: true` means a rapid series of
merges deploys the newest commit rather than queueing.

## One-time repository setup

GitHub Pages must be told to take its content from Actions rather than from
a branch. This is a repository setting and **cannot be done from a
workflow file**:

> **Settings → Pages → Build and deployment → Source → GitHub Actions**

Until that is set, `pages.yml` fails at the `configure-pages` step with a
message about Pages not being enabled. The site appears at
`https://<owner>.github.io/<repo>/` on the first successful deploy.

Permissions used by `pages.yml`:

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

`id-token: write` is required by `actions/deploy-pages@v4`, which uses OIDC
rather than a token.

## What gets deployed

The whole `site/` directory as it sits in the repository, plus
`graph.json` and `details.json`, which the workflow generates during the
build (they are not in git):

```
site/
├── index.html
├── app.css
├── app.js
├── graph.json          ← generated by the workflow, not committed
├── details.json        ← generated by the workflow, not committed
└── vendor/
    ├── cytoscape.min.js
    ├── cytoscape.LICENSE
    └── cytoscape.VERSION
```

No build step, no bundler, no server. Everything is static, and the only
JavaScript dependency is vendored in the repository.

## Why the generated files are not committed

`site/graph.json` and `site/details.json` are build artefacts, and the
workflow regenerates them before deploying, so they are **not in git**
(they are listed in `.gitignore`). Until 2026-10-02 they were committed, for
two stated reasons, which no longer hold up:

1. *"The site works from a clone."* A fresh clone now needs one command
   first: `python tools/build_graph.py`, then
   `python -m http.server --directory site`. `docs/graph-development.md`
   already listed that build as step 2 of local development.
2. *"Graph changes are reviewable."* Each file is a single ~1 MB line of
   JSON, so a pull request "diff" of it is one unreadable line. The
   reviewable change is the entity Markdown, which is still in the diff.

What committing them actually cost was not staleness (which the old
`test_generated_graph_matches_repository` caught) but **merge conflicts**:
every pull request regenerated both files, so once any other pull request
merged first, GitHub reported "merge conflicts" and refused the merge until
the branch was updated and the files were rebuilt. Of seven pull requests
opened in parallel on 2026-10-01, every one except the first to merge hit
this, and four needed a second fix-up commit because the stale copy had been
staged before the rebuild.

The property that makes not committing safe is that the build is
reproducible. `tools/test_build_graph.py::test_build_is_deterministic`
builds twice and requires identical content apart from `generated_at`.

They are still **generated files** — see README §"No manual graph
maintenance". Nobody edits them by hand.

## Verifying a deployment

```bash
# Is the workflow green?
#   → repository → Actions → "Build and deploy Atlas graph"

# Is the site actually serving the current graph?
curl -sI  https://dalust.github.io/Data-Initiatives-Atlas/
curl -s   https://dalust.github.io/Data-Initiatives-Atlas/graph.json \
  | python -c "import json,sys; g=json.load(sys.stdin); print(g['generated_at'], g['stats'])"
```

`generated_at` on the live site should match the time of the most recent
deploy, not the time the file was committed.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `configure-pages` fails: "Pages is not enabled" | The one-time setup above has not been done. |
| Deploy succeeds, site 404s | Pages can take a minute on first publish; also check the URL casing — it is derived from the repository name. |
| Site loads but the graph is empty | `graph.json` failed to fetch. The page shows the HTTP status in an overlay. Check the artefact contains `graph.json`. |
| Deploy did not trigger | The commit touched only paths outside the `paths:` filter. Run the workflow manually via **Actions → Run workflow**. |
| Deploy ran on a pull request | It cannot: `pages.yml` has no `pull_request` trigger. |
